# Listening-led discovery

**R7 source, 23 September 2026 local time.** These contracts describe the working tree after uploaded build **1.0.0 (3)**. [VERIFICATION.md](VERIFICATION.md) records current execution and completed earlier rounds; [release status](app-store/RELEASE_STATUS.md) owns the uploaded baseline.

## User behavior

**Recap > Listening languages** and **Settings > Discovery > Listening languages** show the last 30 days of counted plays. The page reports plays, different songs, language shares and Unclassified. **Tune recommendations** starts collapsed and offers **Automatic**, **More** and **Less** for Bengali (`bn`), English (`en`), Hindi (`hi`), Tamil (`ta`) and Telugu (`te`). Adjustments change recommendations, not the recorded statistics.

Welcome and radio setup require no language selection. Radio says **Languages follow your listening** and keeps era and optional artist hints. Adjustments guide the next Home refresh, new automatic radios and newly generated mixes. A current-period Daily Mix or Discover Weekly is not regenerated by a nudge. An active radio retains its captured profile; a history privacy boundary retires its old derived learning without replacing the playing queue.

Turning history off preserves saved counts and adjustments while stopping new listening-derived checks. Clearing history removes its counts and derived evidence, but keeps explicit language adjustments, recording corrections, likes and playlists. **Reset adjustments** returns the five nudges to Automatic independently of history clearing.

## Counting and recording evidence

[`ListeningAnalytics.languageSummary`](../Sources/Library/ListeningAnalytics.swift#L93) projects the existing recap rather than keeping another play counter:

- A session counts once after **30 seconds**, or halfway through a song shorter than a minute. Missing or invalid duration uses 30 seconds. Additional acknowledged deltas in that session do not create another play.
- The month window uses the session's actual start within the last 30 calendar days. Invalid dates/tracks/seconds, future starts and duplicate session UUIDs are excluded by the existing summary. Pauses and seek jumps do not add listening time.
- Percentages divide by **all counted plays**, including Unclassified. Different songs count recording IDs with a qualifying play. Likely, conflicting, missing and failed classifications remain Unclassified; their plays still count. Ordinary recap time also includes valid listening below the play threshold.
- Queue snapshots, favorites, recent-item visits and provider popularity totals do not create listening events.

Evidence uses the existing [`ArtistSpotlight.languageResult`](../Sources/Core/ArtistSpotlight.swift): a saved recording correction takes priority, then verified recording metadata, then identified automatic evidence. Automatic results are keyed by `LyricsRequestKey`, including recording ID and normalized title, artist, album and duration metadata. A changed recording identity cannot reuse another version's lyrics evidence. `Track.language` currently represents verified Hindi/English metadata; the five-language result type also accepts recording-matched lyrics, configured MusicBrainz work evidence and corrections.

Likely labels remain Unclassified in these counts. Artist nationality, provider region, station wording and another recording by the artist do not prove language. Recognition runs on text, not audio. [SONG_LANGUAGES.md](SONG_LANGUAGES.md) owns classifier thresholds, source provenance and measured accuracy limits.

## Recommendation weights

[`ListeningLanguageProfile`](../Sources/Core/ListeningLanguages.swift#L73) separates observed counts from recommendation weights. For each **observed, identified** language:

```text
base weight = 0.9 * language plays / identified plays
            + 0.1 / number of observed languages
More        = max(0.2, 2 * base weight)
Less        = 0.25 * base weight
```

Weights are normalized after nudges. More can activate an unheard supported language without inventing a count; Less does not activate an unobserved language or ban a language. With no identified plays, saved legacy Hindi/English discovery preferences provide the starting weights, or both languages if that set is empty. The profile remains unlearned until actual identified plays exist. Legacy choices are not migrated into More/Less adjustments.

Unknown-language candidates receive multiplier `1`. Identified candidates receive `0.6 + 1.4 * normalizedWeight`, including a positive value for languages outside the active weights. This is soft ranking, not a language exclusion. Audio eligibility, dislikes, duplicate-song rules and artist caps still apply. Explicit Search remains unrestricted.

`scheduledLanguages(count:)` assigns existing request slots proportionally with deterministic ties. With at least three slots, a second active language can receive an existing slot rather than expanding the budget. The `languages-v1` request key uses five-percent weight buckets and nudges, not recording IDs or raw play counts.

[`RecommendationEngine.languageDiscovery`](../Sources/Recommendations/LanguageDiscoveryRecommendations.swift) produces at most two language shelves, prioritizing More adjustments. Each target can use one known-language recording's radio and one `"<language> songs"` search fallback, at most four catalog calls total. Without a known seed, it starts with the search. Returned neighbors are not certified as that language. A successful empty response stays empty; useful partial results survive another source's failure, while failure of every source remains retryable.

Automatic Daily Mix, Discover Weekly and Because you listen use the profile for seed allocation and candidate ranking. Mix generation retains its ten-call provider budget and period stability. Automatic radio shares its existing startup budgets across all active languages; it does not multiply them by language count. [PROVIDERS.md](PROVIDERS.md#radio-and-language-evidence) owns those radio budgets. Weekly charts retain their India/US/Global reporting scope and dates, rather than becoming certified language charts.

## Automatic checks and derived cache

[`MusicAppModel.refreshListeningLanguages()`](../Sources/App/MusicAppModel.swift#L266) enables checks only when device services are active, listening-history saving is on and connectivity is **not known offline**. Real launches and phone-scene activation enable those services; inactive/background transitions pause the work. Fixture/unit hosts do not automatically start native device services.

Successful durable listening checkpoints refresh eligibility. Home loading, the language page, library recovery and applied cloud changes also refresh the projection. Consequently, bounded recording-metadata and lyrics requests can happen **without opening an artist page or the lyrics sheet**. After cached evidence, `ArtistSpotlightLanguageService` checks official recording audio-language metadata before the composite lyrics provider and configured MusicBrainz fallback. Explicit tags skip recognition; missing/failed metadata keeps the bounded fallback, with recognition on device. [YouTube metadata](YOUTUBE_DATA_API.md) owns that precedence. [Provider requests](PROVIDERS.md#network-requests) and [Privacy](../PRIVACY.md#requests-to-external-services) describe the transmitted metadata.

[`ListeningLanguageDiscovery`](../Sources/Catalog/ListeningLanguageDiscovery.swift) snapshots qualified recent inputs. Corrections and verified metadata bypass provider checks. Repeated checkpoints keep useful in-flight work; changed metadata, removed eligibility and privacy boundaries reject obsolete results.

| Bound | Current value |
| --- | --- |
| Checks authorized by one refresh | At most 12 |
| Concurrent classifications | At most 2, including cancelled work until it unwinds |
| Eligible snapshot / derived entries | At most 512 |
| Pending candidates | At most 128 |
| Derived disk file | At most 2 MiB; schema version 1 |
| Identified-result lifetime | 12 hours |
| Likely, unclassified or failed-check lifetime | 5 minutes |

Each refresh authorizes one pass. Completion callbacks can update statistics but cannot recursively authorize another pass. A source failure becomes `unclassified(.lookupFailed)` at this layer and gets the negative cooldown; cancellation caused by pause/reset/obsolete input publishes no result. This differs from the underlying language service's retryable transport-error cache policy. Source deadlines remain in [PROVIDERS.md](PROVIDERS.md#radio-and-language-evidence).

[`ListeningLanguageDiscoveryCache`](../Sources/Catalog/ListeningLanguageDiscoveryCache.swift) stores `Caches/GanaBajana/listening-language-cache.json` on real launches. Entries contain only the metadata-aware key, result/provenance, `checkedAt` and `expiresAt`. They contain no lyrics text, audio, signed stream URLs, listening events or aggregate play counters. Recording/work IDs can remain in evidence provenance. The file is local, purgeable and excluded from backups on successful writes; it is not part of iCloud library sync.

Reading preserved history while history is off may hydrate valid existing cache evidence; that read does not itself authorize provider checks or a cache rewrite. Reuse requires the current eligible key and `checkedAt <= now < expiresAt`; a clock rollback cannot turn a future check into valid evidence. Pause keeps already accepted evidence and may finish saving that evidence. History clear resets memory and schedules deletion of the derived file. Generation and storage-revision fences reject late loads, checks and older saves; file cleanup has its own outcome, separate from the durable library clear.

Malformed, oversized, unsupported/future or externally replaced cache files are preserved rather than overwritten. `ListeningLanguageDiscovery` can continue with memory-only evidence and a non-success cache status. A failed cache write cannot damage `library.json` or claim disk durability. A nil cache URL is memory-only.

## Fewer repeats in queue shuffle

**Settings > Playback > Shuffle order** offers **Random** and **Fewer repeats**. Random is the missing-field default. The setting is independent of whether Shuffle is currently enabled; changing it does not rearrange the active queue. The next list Shuffle samples the first song and remainder together. Enabling Shuffle around an existing selection keeps that exact occurrence first. Watch and CarPlay shuffle actions use the same player policy.

[`PlaybackShufflePolicy`](../Sources/Playback/PlaybackShufflePolicy.swift) reads durable history only when a new explicit order is produced. The model supplies no evidence while history is off, storage is unavailable or recovery is required. Recent qualified session starts within seven elapsed days receive:

```text
weight = 0.1 + 0.9 * daysSinceQualifiedSessionStart / 7
```

Older/unheard recordings have weight 1. Sampling uses independent exponential priorities without replacement per queue occurrence; every occurrence remains eligible and repeats remain possible. Session checkpoints contribute their maximum saved seconds, not a sum. Conflicting identities, invalid/future input and unqualified sessions supply no recency evidence. No provider popularity total or additional listening counter is used.

Restored playback keeps its saved order and stays paused. New snapshots include optional `PlaybackSnapshot.originalQueueIndices`, a validated permutation identifying each playback occurrence's original position. This preserves identical duplicates through unshuffle after relaunch. Legacy snapshots keep recording-based matching and retain the absent field during passive restore/checkpoints; actual queue-order or selected-occurrence edits can add it. Malformed present mappings fail library validation, and mapping-only saves remain device-local. Explicit queue edits and Repeat one keep their meaning.

## Familiar versus new discovery

**Settings > Discovery > Discovery balance** offers **More familiar**, **Balanced** and **More new**. Balanced is the missing-field default. The setting guides new Home shelves and future generated mixes; a saved current-period Daily Mix or Discover Weekly retains its songs. Home request/cache identity and mix publication guards capture the preference, so a late response cannot restore an obsolete choice. Current playback and active radio are preserved.

| Choice | Daily Mix familiar target | Weekly known-artist multiplier | Home shelf familiar/new multipliers |
| --- | --- | --- | --- |
| More familiar | 70%, rounded to 18 of 25 | 1.0 | 1.5 / 1.0 |
| Balanced | 40%, 10 of 25 | 0.55 | 1.0 / 1.0 |
| More new | 15%, rounded to 4 of 25 | 0.25 | 1.0 / 1.5 |

Familiar recordings use existing `TasteProfile.heardTrackIDs`: saved music, prior listening and recents, including a short heard recording with no affinity score. Provider-returned heard songs stay in that pool for every mode. Daily Mix reserves achievable unheard artist capacity, then relaxes the target only when eligible pools or artist limits require it. Discover Weekly remains unheard recordings in all modes; its existing top-10 familiar-artist set controls the multiplier. Shelf boosts multiply independent language weights and remain positive. Existing provider budgets, dislikes and artist caps apply.

Both preferences are independent scalar sync registers. Missing fields in current sparse journals do not require new revisions or a schema bump. Present invalid values are rejected. A shuffle-only or clock-only cloud merge applies preference services without invalidating Home; combined content/history changes still refresh discovery after the durable merge.

## Cache retention from listening

[`AudioCacheRetentionPolicy`](../Sources/Playback/AudioCacheRetentionPolicy.swift) is a separate local projection of durable listening events. It uses the actual session start, not start plus listened seconds, since a paused session has no inferred end time. Matching repeated checkpoints contribute one session using the greatest acknowledged duration; conflicting session identities contribute nothing.

```text
score = 0.55 * 2^(-daysSinceActualSessionStart / 7)
      + 0.45 * log1p(min(qualifiedPlays30Days, 20)) / log(21)
```

The recency term is zero after 90 days. Frequency uses qualified sessions in the last 30 days and caps at 20. These are elapsed-day windows; both terms age when scored without requiring another listening update. Lower scores are evicted first, with older actual listening, cache access time and recording ID breaking ties. Cache reads are tie-breakers, not hidden listening events. History off keeps existing evidence but creates no new listening signal; clearing history removes the derived signal while ordinary cache-access ordering remains.

Complete audio files have **no TTL**. Eviction instead enforces the byte and logical-song policy in [PROVIDERS.md](PROVIDERS.md#audio-cache-and-quality). Current, upcoming, outgoing and native-reader files are protected across all variants; protected files can leave a reported overage. Speculative admission cannot evict a higher-scored recording and checks the complete victim set before deleting anything. Explicit foreground playback can admit new music under the normal policy. Scores are neither synced aggregate counters nor a permanent offline-download promise.
