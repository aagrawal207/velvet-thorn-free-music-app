# Listening-led discovery

**R7 source, 23 September 2026 local time.** These contracts describe the working tree after uploaded build **1.0.0 (3)**. [VERIFICATION.md](VERIFICATION.md) records current execution and completed earlier rounds; [release status](app-store/RELEASE_STATUS.md) owns the uploaded baseline.

## User behavior

**Recap > Listening languages** and **Settings > Discovery > Listening languages** show the last 30 days of counted plays. The page reports plays, different songs, language shares and Unclassified. **Tune recommendations** starts collapsed and offers **Automatic**, **More** and **Less** for Bengali (`bn`), English (`en`), Hindi (`hi`), Tamil (`ta`) and Telugu (`te`). Adjustments change recommendations, not the recorded statistics.

Welcome and Radio require no language selection. Song/artist Radio starts directly, with optional language and familiarity controls in **Tune Radio** for future additions. Automatic language uses the current listening profile; an explicit choice excludes unknown or mismatched recordings. Adjustments guide the next Home refresh and newly generated mixes; a current-period Daily Mix or Discover Weekly is not regenerated by a nudge. A history privacy boundary retires old radio work without replacing the playing queue. [SEED_RADIO.md](SEED_RADIO.md) owns the active Radio contract; legacy experience-radio callers retain their captured-profile behavior.

Turning history off preserves saved counts and adjustments while stopping new listening-derived checks. Clearing history removes its counts and derived evidence, but keeps explicit language adjustments, recording corrections, likes and playlists. **Reset adjustments** returns the five nudges to Automatic independently of history clearing.

## Counting and recording evidence

[`ListeningAnalytics.languageSummary`](../Sources/Library/ListeningAnalytics.swift#L93) projects the existing recap rather than keeping another play counter:

- A session counts once after **30 seconds**, or halfway through a song shorter than a minute. Missing or invalid duration uses 30 seconds. Additional acknowledged deltas in that session do not create another play.
- The month window uses the session's actual start within the last 30 calendar days. Invalid dates/tracks/seconds, future starts and duplicate session UUIDs are excluded by the existing summary. Pauses and seek jumps do not add listening time.
- Percentages divide by **all counted plays**, including Unclassified. Different songs count recording IDs with a qualifying play. Likely, conflicting, missing and failed classifications remain Unclassified; their plays still count. Ordinary recap time also includes valid listening below the play threshold.
- Queue snapshots, favorites, recent-item visits and provider popularity totals do not create listening events.

Evidence uses the existing [`ArtistSpotlight.languageResult`](../Sources/Core/ArtistSpotlight.swift): a saved recording correction takes priority, then verified recording metadata, then identified automatic evidence. Automatic results are keyed by `LyricsRequestKey`, including recording ID and normalized title, artist, album and duration metadata. A changed recording identity cannot reuse another version's lyrics evidence. `Track.language` currently represents verified Hindi/English metadata; the five-language result type also accepts recording-matched lyrics, configured MusicBrainz work evidence and corrections.

Likely labels remain Unclassified in these counts. Artist nationality, provider region, station wording and another recording by the artist do not prove language. Recognition runs on text, not audio. [SONG_LANGUAGES.md](SONG_LANGUAGES.md) owns classifier thresholds, source provenance and measured accuracy limits.

## Recommendation weights

[`ListeningLanguageProfile`](../Sources/Core/ListeningLanguages.swift#L73) separates observed counts from recommendation weights. For each **observed, identified** language:

```text
base weight = 0.9 * language plays / identified plays
            + 0.1 / number of observed languages
More        = max(0.2, 2 * base weight)
Less        = 0.25 * base weight
```

Weights are normalized after nudges. More can activate an unheard supported language without inventing a count; Less does not activate an unobserved language or ban a language. With no identified plays, saved legacy Hindi/English discovery preferences provide the starting weights, or both languages if that set is empty. The profile remains unlearned until actual identified plays exist. Legacy choices are not migrated into More/Less adjustments.

Unknown-language candidates receive multiplier `1`. Identified candidates receive `0.6 + 1.4 * normalizedWeight`, including a positive value for languages outside the active weights. This is soft ranking, not a language exclusion. Audio eligibility, dislikes, duplicate-song rules and artist caps still apply. Explicit Search remains unrestricted.

`scheduledLanguages(count:)` assigns existing request slots proportionally with deterministic ties. With at least three slots, a second active language can receive an existing slot rather than expanding the budget. The `languages-v1` request key uses five-percent weight buckets and nudges, not recording IDs or raw play counts.

[`RecommendationEngine.languageDiscovery`](../Sources/Recommendations/LanguageDiscoveryRecommendations.swift) produces at most two language shelves, prioritizing More adjustments. Each target can use one known-language recording's radio and one `"<language> songs"` search fallback, at most four catalog calls total. Without a known seed, it starts with the search. Returned neighbors are not certified as that language. A successful empty response stays empty; useful partial results survive another source's failure, while failure of every source remains retryable.

Automatic Daily Mix, Discover Weekly and Because you listen use the profile for seed allocation and candidate ranking. A super like ([SUPER_LIKES.md](SUPER_LIKES.md)) changes only the affinity input: `TasteProfile.superLikeBoost` (540, three times `favoriteBoost`) credits the recording and its artists instead of the like credit, and `superLikedTrackIDs` sits beside `heardTrackIDs`. `RecommendationEngine.Seeds.init(profile:languageProfile:periodKey:)` and `scopedSeeds(..., periodKey:)` reserve one of the four recording seeds for an eligible super liked recording (recommendable, not disliked) whenever one exists, rotating by period key through `jitter(periodKey:id:)`; `composeDailyMix` leads each Daily Mix's familiar pool with one eligible super like from its scope, rotating by day key within the familiar share and the artist cap. Discover Weekly stays unheard-only, so a super liked song never appears in it while its neighbours and artist affinity do. Up to three Daily Mixes are built from distinct taste clusters over genre family, recording language and session co-occurrence, sharing the single mix's ten-call budget with no recording in two mixes; thin history keeps one Daily Mix ([DAILY_MIXES.md](DAILY_MIXES.md)). Mix generation retains its ten-call provider budget and period stability. Automatic radio shares its existing startup budgets across all active languages; it does not multiply them by language count. [PROVIDERS.md](PROVIDERS.md#radio-and-language-evidence) owns those radio budgets. Weekly charts retain their India/US/Global reporting scope and dates, rather than becoming certified language charts.

A genre affinity term composes with the language multiplier and the familiarity tier ([GENRE_PROFILE.md](GENRE_PROFILE.md)). `ListeningGenreProfile` mirrors this profile over the same qualified plays in the last 30 days, using MusicBrainz genre evidence per recording and artist, with its own More/Automatic/Less nudges per genre family (`UserPreferences.genreNudges`). Home shelves (`becauseYouListen`, `languageDiscovery`) multiply a candidate's score by a bounded genre factor (1.0 to 1.15 by the dominant family's relative weight, 0.85 for a family set to Less, exactly 1 without evidence or before the profile has learned), so it reorders near ties but cannot beat the 1.5x familiarity tier or the 0.6 to 2.0 language range above. Daily Mix and Discover Weekly apply the same term only once at least 40 percent of the window's plays are classified and only to candidates whose dominant family is in the top three (or nudged Less); artist caps and dislikes are unchanged. Search > Radio orders stations within each group by genre affinity without changing station content. Genre nudges change weights, never the recorded statistics, and the derived genre evidence file is device-local like the language cache.

## Automatic checks and derived cache

[`MusicAppModel.refreshListeningLanguages()`](../Sources/App/MusicAppModel.swift#L266) enables checks only when device services are active, listening-history saving is on and connectivity is **not known offline**. Real launches and phone-scene activation enable those services; inactive/background transitions pause the work. Fixture/unit hosts do not automatically start native device services.

Successful durable listening checkpoints refresh eligibility. Home loading, the language page, library recovery and applied cloud changes also refresh the projection. Consequently, bounded recording-metadata and lyrics requests can happen **without opening an artist page or the lyrics sheet**. After cached evidence, `ArtistSpotlightLanguageService` checks official recording audio-language metadata before the composite lyrics provider and configured MusicBrainz fallback. Explicit tags skip recognition; missing/failed metadata keeps the bounded fallback, with recognition on device. [YouTube metadata](YOUTUBE_DATA_API.md) owns that precedence. [Provider requests](PROVIDERS.md#network-requests) and [Privacy](../PRIVACY.md#requests-to-external-services) describe the transmitted metadata.

[`ListeningLanguageDiscovery`](../Sources/Catalog/ListeningLanguageDiscovery.swift) snapshots qualified recent inputs. Corrections and verified metadata bypass provider checks. Repeated checkpoints keep useful in-flight work; changed metadata, removed eligibility and privacy boundaries reject obsolete results.

| Bound | Current value |
| --- | --- |
| Checks authorized by one refresh | At most 12 |
| Concurrent classifications | At most 2, including cancelled work until it unwinds |
| Eligible snapshot / derived entries | At most 512 |
| Pending candidates | At most 128 |
| Derived disk file | At most 2 MiB; schema version 1 |
| Identified-result lifetime | 12 hours |
| Likely, unclassified or failed-check lifetime | 5 minutes |

Each refresh authorizes one pass. Completion callbacks can update statistics but cannot recursively authorize another pass. A source failure becomes `unclassified(.lookupFailed)` at this layer and gets the negative cooldown; cancellation caused by pause/reset/obsolete input publishes no result. This differs from the underlying language service's retryable transport-error cache policy. Source deadlines remain in [PROVIDERS.md](PROVIDERS.md#radio-and-language-evidence).

[`ListeningLanguageDiscoveryCache`](../Sources/Catalog/ListeningLanguageDiscoveryCache.swift) stores `Caches/GanaBajana/listening-language-cache.json` on real launches. Entries contain only the metadata-aware key, result/provenance, `checkedAt` and `expiresAt`. They contain no lyrics text, audio, signed stream URLs, listening events or aggregate play counters. Recording/work IDs can remain in evidence provenance. The file is local, purgeable and excluded from backups on successful writes; it is not part of iCloud library sync.

Reading preserved history while history is off may hydrate valid existing cache evidence; that read does not itself authorize provider checks or a cache rewrite. Reuse requires the current eligible key and `checkedAt <= now < expiresAt`; a clock rollback cannot turn a future check into valid evidence. Pause keeps already accepted evidence and may finish saving that evidence. History clear resets memory and schedules deletion of the derived file. Generation and storage-revision fences reject late loads, checks and older saves; file cleanup has its own outcome, separate from the durable library clear.

Malformed, oversized, unsupported/future or externally replaced cache files are preserved rather than overwritten. `ListeningLanguageDiscovery` can continue with memory-only evidence and a non-success cache status. A failed cache write cannot damage `library.json` or claim disk durability. A nil cache URL is memory-only.

## Fewer repeats in queue shuffle

**Settings > Playback > Shuffle order** offers **Random** and **Fewer repeats**. Fewer repeats is the new-install and missing-field default; explicitly stored Random is preserved. The setting is independent of whether Shuffle is currently enabled; changing it does not rearrange the active queue. The next list Shuffle samples the first song and remainder together. Enabling Shuffle around an existing selection keeps that exact occurrence first. Watch and CarPlay shuffle actions use the same player policy.

[`PlaybackShufflePolicy`](../Sources/Playback/PlaybackShufflePolicy.swift) reads durable history only when a new explicit order is produced. The model supplies no evidence while history is off, storage is unavailable or recovery is required. Recent qualified session starts within seven elapsed days receive:

```text
weight = 0.1 + 0.9 * daysSinceQualifiedSessionStart / 7
```

Older/unheard recordings have weight 1. Sampling uses independent exponential priorities without replacement per queue occurrence; every occurrence remains eligible and repeats remain possible. Session checkpoints contribute their maximum saved seconds, not a sum. Conflicting identities, invalid/future input and unqualified sessions supply no recency evidence. No provider popularity total or additional listening counter is used.

Restored playback keeps its saved order and stays paused. New snapshots include optional `PlaybackSnapshot.originalQueueIndices`, a validated permutation identifying each playback occurrence's original position. This preserves identical duplicates through unshuffle after relaunch. Legacy snapshots keep recording-based matching and retain the absent field during passive restore/checkpoints; actual queue-order or selected-occurrence edits can add it. Malformed present mappings fail library validation, and mapping-only saves remain device-local. Explicit queue edits and Repeat one keep their meaning.

## Familiar versus new discovery

**Settings > Discovery > Discovery balance** offers **More familiar**, **Balanced** and **More new**. Balanced is the missing-field default. The setting guides new Home shelves and future generated mixes; a saved current-period Daily Mix or Discover Weekly retains its songs. Home request/cache identity and mix publication guards capture the preference, so a late response cannot restore an obsolete choice. Current playback and active radio are preserved.

| Choice | Daily Mix familiar target | Weekly known-artist multiplier | Home shelf familiar/new multipliers |
| --- | --- | --- | --- |
| More familiar | 70%, rounded to 18 of 25 | 1.0 | 1.5 / 1.0 |
| Balanced | 40%, 10 of 25 | 0.55 | 1.0 / 1.0 |
| More new | 15%, rounded to 4 of 25 | 0.25 | 1.0 / 1.5 |

Familiar recordings use existing `TasteProfile.heardTrackIDs`: saved music, prior listening and recents, including a short heard recording with no affinity score. Provider-returned heard songs stay in that pool for every mode. Daily Mix reserves achievable unheard artist capacity, then relaxes the target only when eligible pools or artist limits require it; its one super-like head pick counts inside the familiar target. Discover Weekly remains unheard recordings in all modes, super liked songs included; its existing top-10 familiar-artist set controls the multiplier. Shelf boosts multiply independent language weights and remain positive. Existing provider budgets, dislikes and artist caps apply.

### Discover Weekly: unheard, unlikely to be known, and some deep cuts

A Weekly candidate is dropped when any of these holds:

1. Its exact recording ID is in `TasteProfile.heardTrackIDs`: every retained listening session (any length, including a half-second tap; history is retained 400 days), recents, likes and super likes, playlist songs and dislikes.
2. It is the same song as a heard or disliked one under another ID (`SongIdentity.key`: `SongTitle.core` of the title plus the normalised first credited artist). This covers re-uploads, album and single IDs, `saavn:` and `gaana:` copies, and remix, live or "From the film" versions. Two IDs of one unheard song also appear only once.
3. It is a likely-known hit: among the first five of a familiar artist's top songs (`likelyKnownTopSongs`; the same top-10 familiar artists as the multiplier). A new artist's hits stay eligible.
4. It rests after early skips, by recording ID or song key ([Skips, completions and replays](#skips-completions-and-replays-in-recommendations)).

Songs played while history was off, before Clear History, more than 400 days ago or only in another app are unknown to Velvet Thorn; rules 2 and 3 are what reduce outside-app repeats. Matching by title and first artist can, rarely, also drop a different song with the same title by the same artist.

**Deep cuts.** `WeeklyPopularity` estimates each candidate's popularity within this week's harvest. A provider play count (`Track.playCount`) becomes a percentile among the same source's known counts, never across sources, and only when that source has at least five counts. Otherwise the estimate comes from the harvest: top-songs position 0 to 4 is 0.85, 5 to 9 is 0.6, later 0.45; a radio-only song is 0.5 within a radio's first ten and 0.3 beyond; each additional list that surfaced it adds 0.15. A missing count is unknown, never unpopular by itself. A deep cut has an estimate of at most 0.4. `composeDiscoverWeekly` reserves 20, 35 or 50 percent of the 30 songs (6, 11 or 15) for deep cuts under More familiar, Balanced or More new, picks the best-ranked ones, spreads them evenly through the list, and fills the rest with the ranked songs, then any remaining deep cuts, so the quota never shortens the Weekly. One artist cap of two and one song key apply across the whole list. No provider calls are added; the ten-call budget is unchanged.

Both preferences are independent scalar sync registers. Missing fields in current sparse journals do not require new revisions or a schema bump. Present invalid values are rejected. A shuffle-only or clock-only cloud merge applies preference services without invalidating Home; combined content/history changes still refresh discovery after the durable merge.

## Skip and completion signals

`PlayerController.onListeningSignal` reports how each music listening session ended, and `ListeningSignalStore` keeps the result on this device. A [`ListeningSignal`](../Sources/Core/ListeningSignals.swift) holds the recording ID, title, credited artist names, end time, credited seconds, known duration, ending, origin and a rapid flag. Credited seconds come from the same listening clock as history, so pauses and seek jumps never count. Duration is the playing stream's duration when known, then the catalog duration, otherwise unknown. [Skips, completions and replays](#skips-completions-and-replays-in-recommendations) owns how recommendations weigh them.

A session ends with at most one signal, and only when it has credited audio. Live Radio never records one. Playing means playback intent without an active audio interruption.

| Session end | Signal |
| --- | --- |
| Next while playing; a queue jump to another entry while playing; a new list, shuffle or radio start that replaces the playing song | `skipped` |
| The song reaches its end; a crossfade or Automix blend hands over to the next song; Repeat One restarts it | `completed` |
| The song ends within 2 seconds of a listener seek (`seek(to:)`) with less than half of it heard | `skipped` while playing, nothing while paused |
| Next while paused; Previous, restart or back; removing the playing song; the dislike auto-skip (`next(recordsSignal: false)`); tapping the playing song or its queue entry again; playback errors; no credited audio | Nothing |

Offline Next and offline song ends follow the same rules. Next at the end of the queue only pauses, so it records nothing. SponsorBlock jumps and recovery seeks are not listener seeks. A privacy discard of pending listening (History Off, History On or Clear History) records nothing and starts a new session, so earlier seconds never reach a later signal.

**Origin.** A song is `generated` when it plays in a radio session, is a seed-radio addition, came from Autoplay (`autoplayTrackIDs`) or is an occurrence a generated mix supplied. Everything else is `chosen`. `MusicAppModel.play` recognises a mix when the list it receives has exactly the recordings of a saved Discover Weekly or Daily Mix (`library.mixes`) or a current Moment mix, then passes `origin: .generated` to `PlayerController.play` or `playShuffled`. The player keeps that provenance per occurrence, so songs added to the queue later stay `chosen`. Provenance is not saved with the queue: a queue restored after relaunch or Live Radio counts as chosen.

**Rapid.** A skip is rapid when it is at least the third skip within 20 seconds (`ListeningSignalWeights.rapidWindow`, `rapidCount`), timed on the monotonic clock and counted in this process only. A skip before any audio records no signal but still counts towards the window.

**Storage.** `ListeningSignalStore` writes `Application Support/GanaBajana/listening-signals.json` beside the library: a version-1 document with the library's history epoch and the signals, oldest first.

| Bound | Value |
| --- | --- |
| Signals | At most 2,048; the oldest go first |
| Age | 90 days, applied on load and on every write |
| File | 1 MiB read cap; the oldest signals give way if long names would exceed it |
| Text | Titles and artist names trimmed to 200 characters, at most 16 artists |
| Writes | Coalesced for 2 seconds, then one atomic same-folder rename; flushed when device services deactivate |

`signals` and `revision` change after a durable write, and a privacy erase is visible at once. `MusicAppModel` exposes `listeningSignals` and `listeningSignalsRevision`; `TasteProfileCacheKey` includes the revision, so a new skip rebuilds the profile. Fixture and unit hosts use a memory-only store that publishes at once.

**Privacy.** The file is marked excluded from backup before it is installed. It is never synced and never part of the library document, iCloud replicas, widgets or companions. Recording needs Save Listening History. History Off and Clear History erase the store through the same library hooks and history epoch as `RadioHistoryStore`, and a relaunch under a different epoch clears signals from a reset the app missed. After a failed library load the store waits, unread and unchanged, until a successful load supplies a trustworthy epoch. A corrupt, unsupported, newer-version, oversized or unknown-field file, a folder in its place, or a write that finds the file changed blocks the store: the file is kept, `isBlocked` and `errorMessage` report it, and nothing is recorded. An erase requested while blocked stays pending and wins over recovered signals. **Reload saved library** retries a blocked store.

**Metrics.** Category `ListeningSignals`. Neither event carries a recording ID, title, artist or any other unbounded value.

| Event and fields | Emitted when | Values |
| --- | --- | --- |
| `event=listening_signal ending origin rapid strength recorded reason` | The player reports a signal and the store keeps or drops it | `ending` skipped/completed; `origin` generated/chosen; `rapid` 0/1; `strength` strong/mild/light/none (the skip's base band); `recorded` 0/1; `reason` none, history_off or blocked (blocked also covers a deferred epoch and an invalid signal) |
| `event=listening_signal_store outcome count` | A load, write, erase, failed write or blocked load | `outcome` loaded/saved/erased/failed/blocked; `count` retained signals |

## Skips, completions and replays in recommendations

Recommendations read how a song ended, not only that it played. Each ending is a device-local [`ListeningSignal`](../Sources/Core/ListeningSignals.swift); [`TasteProfile.build(..., signals:now:)`](../Sources/Recommendations/TasteProfile.swift) combines signals with the existing listening events, and [`SkipSignals.swift`](../Sources/Recommendations/SkipSignals.swift) holds the rest rule (`SkipEvidence`, `RestingSongs`).

**Skip weight.** `ListeningSignalWeights.skipWeight` gives each skip:

```text
strength = 1.0 before 10 s, 0.4 before 30 s, 0.15 before half the song (or with no known length), 0 from half on
weight   = strength * 0.5 if the listener chose the list * 0.5 if rapid (third skip within 20 s)
         * 0.5 ^ (days since the skip / 14)
```

A finished song weighs 0, and a skip dated in the future counts as today.

**Skip score.** A recording's score is the sum of its skip weights. A song's score sums every upload and version with the same `SongIdentity.key` (title core plus first credited artist), and a candidate uses the larger of the two. A completed signal for the same song, by ID or song key, forgives every skip before it: those skips leave no score, discount or penalty, and only later skips count.

**Rest.** A recording or song rests while its score is at least 1.5. Two early skips of songs Velvet Thorn chose rest a song for about six days and three for about two weeks; skips in a list the listener chose count half, so four early ones rest a song for about six days. One early and one mild skip (1.4) never rest it. A liked or super liked song never rests under any upload, because the like proves the opposite; its skips still apply the discount and penalties below. Resting is not a dislike: the song plays whenever the listener picks it, and it returns once its skips decay below 1.5.

**Affinity.** Each counted skip removes `45 * weight` seconds (`artistPenaltySeconds`) from every credited artist's affinity and from the recording's own affinity, floored at 0, after every positive credit. Two bonuses come from the existing events, with no new storage:

- Finished play: a qualified event whose listened seconds reach `min(0.9 * duration, duration - 10 s)` earns 25 percent more of its decayed weight (`completionBonus`). A missing duration earns no bonus.
- Replays: n qualified plays of a recording started in the last 7 days add `60 * log2(n)` seconds (`replayBonusSeconds`: 60, 120 and 180 for 2, 4 and 8 plays), decayed with the 21-day half-life from the latest play, to the recording and each credited artist. A single play adds nothing, so doubling the plays adds only another 60 s.

Signals carry no session identity, so a completed signal cannot be matched to its listening event reliably. Finished-play and replay credit therefore come from events only; a completed signal only forgives skips. History off records no events and earns no bonus.

| Surface | Effect |
| --- | --- |
| Discover Weekly | Resting recordings and other uploads of resting songs are dropped. Other skipped candidates score `score * (1 - min(0.5, 0.25 * skip score))` before jitter |
| Daily Mix 1 to 3 | The same rules in the provider pool, the familiar pool and the unscored heard fallback, on the single and clustered paths. Resting songs do not shape taste clusters |
| Mix seeds | A resting recording never seeds a radio, in `Seeds` or `scopedSeeds`. The super-like reservation is unaffected because a super like cannot rest |
| Because you like, language shelves | Resting songs are dropped, and a language shelf never seeds from one |
| Song and artist Radio | Additions drop resting songs. An artist's resting popular songs do not anchor its radio unless all of them rest. Radio from a song the listener picks starts whatever its skips, and frozen anchors are never removed |
| Autoplay | `RestingSongs.excluding(_:)` drops resting songs from each continuation batch and `AutoplayContinuation.fallbackSeed(..., resting:)` never seeds from one; `MusicAppModel` supplies the profile's `restingSongs` |

No surface makes a provider call to replace a resting song; budgets are unchanged, and Radio's existing single fresh retry stays the only follow-up when every answered song is filtered. Mixes remain stable within their period key: one profile is captured per generation and the discount is applied before the period jitter.

**Metrics.** `event=skip_signals_applied scope=<discover_weekly|daily_mix|seed_radio|home> resting_excluded=<n> downweighted=<n> artists_penalized=<n>` (category `Recommendations`) is emitted once per Discover Weekly generation that reaches ranking, once per Daily Mix generation (single or clustered), once per Because you like or language shelf operation (`home`), and once per Radio refill or artist anchor lookup (`seed_radio`). `resting_excluded` counts distinct eligible recordings dropped for resting: provider candidates, plus heard recordings for Daily Mix. `downweighted` counts kept Weekly and Daily Mix candidates with a discount. `artists_penalized` counts artists whose affinity skips lowered, and is 0 for Radio, which reads no profile. Building the profile logs nothing.

## Cache retention from listening

[`AudioCacheRetentionPolicy`](../Sources/Playback/AudioCacheRetentionPolicy.swift) is a separate local projection of durable listening events. It uses the actual session start, not start plus listened seconds, since a paused session has no inferred end time. Matching repeated checkpoints contribute one session using the greatest acknowledged duration; conflicting session identities contribute nothing.

```text
score = 0.55 * 2^(-daysSinceActualSessionStart / 7)
      + 0.45 * log1p(min(qualifiedPlays30Days, 20)) / log(21)
```

The recency term is zero after 90 days. Frequency uses qualified sessions in the last 30 days and caps at 20. These are elapsed-day windows; both terms age when scored without requiring another listening update. Lower scores are evicted first, with older actual listening, cache access time and recording ID breaking ties. Cache reads are tie-breakers, not hidden listening events. History off keeps existing evidence but creates no new listening signal; clearing history removes the derived signal while ordinary cache-access ordering remains.

Complete audio files have **no TTL**. Eviction instead enforces the byte and logical-song policy in [PROVIDERS.md](PROVIDERS.md#audio-cache-and-quality). Current, upcoming, outgoing and native-reader files are protected across all variants; protected files can leave a reported overage. Speculative admission cannot evict a higher-scored recording and checks the complete victim set before deleting anything. Explicit foreground playback can admit new music under the normal policy. Scores are neither synced aggregate counters nor a permanent offline-download promise.
