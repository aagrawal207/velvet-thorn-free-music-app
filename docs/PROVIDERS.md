# Velvet Thorn providers and data handling

Velvet Thorn contacts external providers directly from the device. There is no Breezy-operated catalog, account, analytics, or music server. Watch and CarPlay controls use that same phone player and its configured providers. Music-specific browsing can operate without an account; the official recording-metadata path uses an app-restricted developer key. Providers can restrict requests. Account-cookie-free requests still disclose network addresses and requested content.

**R18 source inventory.** Features and model/player hooks are implemented and integrated; verification is in progress. [VERIFICATION.md](VERIFICATION.md) owns counts and results. Feature documents own request recipes and bounded metric/unit/integration tables. R18 adds Radio Browser/broadcaster requests and separately confirmed YouTube account changes. Extractor import is manual, with no feed or publisher key configured. Gain-up, source provenance and export timing/share corrections add no network recipient; export artwork uses the existing loader.

Earlier build-7 R17 verification retains its scope. [ROADMAP.md](ROADMAP.md) owns current direction and [APPSTORE_TESTFLIGHT.md](APPSTORE_TESTFLIGHT.md) owns remote records. Provider/content authorization remains unresolved; undocumented endpoints, extraction and complete-file caching are unofficial. Upload success is not permission.

Relevant provider terms are the [YouTube Terms of Service](https://www.youtube.com/static?template=terms) and [YouTube API Services Developer Policies, section III.E.1](https://developers.google.com/youtube/terms/developer-policies#e.-handling-youtube-data-and-content), which restrict downloading/caching audiovisual content without prior written approval and making it available offline. The developer policies also address undocumented APIs and scraping. A public endpoint, successful extraction, a sign-in session, or a software license does not establish content-distribution rights. Calling complete downloads a “temporary cache” does not supply permission.

[RELEASE_STATUS.md](app-store/RELEASE_STATUS.md) records the dormant release hold. No authorization or content-rights declaration has been prepared as if it were granted.

Local liked-song/playlist filtering and known-offline Search use saved metadata. Home/search prefetch can request music before a play tap. ### Response limits and cancellation

Catalog, recording metadata, MusicBrainz, fast-path playback lookup, and artwork use [`URLSession.boundedData(for:maximumBytes:delegate:)`](../Sources/Networking/BoundedURLSession.swift). It checks both declared length and bytes received, including chunked responses without a known length. The optional task delegate lets the Data API refuse redirects. An oversized response or cancelled caller stops that request's task without invalidating unrelated requests. HTTP status and payload validation remain caller-owned. Declared length is an upper bound, not an EOF equality check, because the networking stack may decode the response body.

| MusicBrainz metadata | 2 MiB | At most 3 seconds within the shared 6-second provider lookup deadline; Song details at most 3 requests within a 12-second deadline; genre classification at most 3 requests per recording |
| YouTube Data API metadata | 256 KiB | Two seconds, within the caller's existing lookup deadline |
| YouTube InnerTube `player` for Song details | 1 MiB | 8 seconds; 2 concurrent requests, identical lookups coalesced |

| JioSaavn API (`JioSaavnTransport`) | 4 MiB | 8 seconds per request, 16 seconds per resource; 4 connections per host, 8 requests per second sliding window, one retry after 350 ms for timeout/connection loss/5xx |
| JioSaavn media probe | 1 KiB range | 8 seconds; requires 200/206, an `audio/mp4`-family content type and an `ftyp` prefix |

These bounds apply to individual responses; higher-level operations can make several requests within their own budgets. Complete media downloads use separate file-length and native-media validation.

[`ExtractionTransport`](../Vendor/YouTubeKit/Sources/YouTubeKit/ExtractionTransport.swift) uses an ephemeral session without automatic cookies, stored credentials, or a URL cache. It enforces receive-time byte limits and deadlines. Full player extraction uses structured concurrent work; cancellation retires its requests rather than cancelling a shared session.

`ArtworkLoader` coalesces work by URL and requested pixel size. Each consumer has its own cancellation: a remaining consumer keeps the transfer alive, while the last cancellation retires and cancels it. Cache clearing waits for retired transfers before removing cached responses. Its non-renewing deadline prevents a trickle response from continually extending the resource budget.

Opening a player's artist-choice list can fetch artist-page metadata for linked IDs, or one exact-name artist search for a name-only credit, followed by the provider's picture URL. `ArtistArtworkResolver` allows two concurrent lookups and a five-second total budget, including queue and image time. Its 128-entry URL/miss cache retries failures after 30 seconds. Names remain immediately selectable; no album/song fallback or extra search page is requested for a picture.

## Catalog, charts, and personal discovery

The official `YouTubeDataAPI` path is recording metadata, not a replacement music catalog or playback provider. It selects `defaultAudioLanguage` and duration for classification, and the same one-unit `videos.list` request (parts `snippet,contentDetails,statistics`) also selects `snippet(description,channelTitle,publishedAt)` and `statistics(viewCount)` for Song details; nothing else is requested and no second call is made for those fields. It reuses bounded cached results, and respects quota/rate/auth backoff. Explicit audio-language tags can skip lyrics and recognition. Missing metadata retains the existing fallback; valid durations and song-play counts are preserved. [YOUTUBE_DATA_API.md](YOUTUBE_DATA_API.md) records configuration, scope, metrics and tests.

[`YouTubeMusicService`](../Sources/Catalog/YouTubeMusicService.swift) uses an ephemeral, account-cookie-free [`CatalogTransport`](../Sources/Catalog/CatalogTransport.swift), without credential storage or a disk response cache. Catalog requests use `WEB_REMIX`, English UI context, and `gl: IN`; chart requests select their own region. Provider visitor/continuation values can still associate requests. Audio rows are preferred and batch-validated; explicit video and podcast rows are excluded from search, radio, artist and album pages. Playlist pages (`VL…` browse ids, including continuations) are the exception: a row without album-audio confirmation lists as its own video entry with `isAudioRecording == false`, a credits-linked album recording confirmed through `get_queue` replaces its clip in place, and podcast-typed and greyed-out rows stay out. Home discovery, radio stations, mixes, autoplay seeds and metadata lookups still skip video entries. [PLAYLIST_BROWSE_FIX.md](PLAYLIST_BROWSE_FIX.md) records the live evidence.

Search from the Search screen fans out to every enabled catalog source at once ([`CompositeCatalog`](../Sources/Catalog/CompositeCatalog.swift)): YouTube Music leads and cannot be disabled; JioSaavn and Gaana each answer with their first page when enabled in Settings > Discovery > Catalog sources and are dropped from that search after the six-second secondary deadline or a failure. Internal lookups (artist matching, radio seeds, spotlight counts, artist artwork, release checks) stay with one provider. Browse, artist, radio and lyrics route by the id prefix (`saavn:`, `gaana:`, bare for YouTube), so a saved prefixed song keeps working with its source switched off. The JioSaavn and Gaana recipes, bounds, identity scheme, stream decryption and quality tiers are in [JIOSAAVN.md](JIOSAAVN.md) and [GAANA.md](GAANA.md); both are unofficial and undocumented.

Home uses [`RecommendationEngine.languageDiscovery`](../Sources/Recommendations/LanguageDiscoveryRecommendations.swift) with the local listening-language profile. Identified counted plays and independent nudges choose bounded recording-radio/search targets across five supported languages; cold start uses the preserved Hindi/English defaults. Candidate language is not certified by the query. The older [`CatalogDiscovery`](../Sources/Catalog/CatalogDiscovery.swift) provider helper remains available, and the model still excludes `editorial-hindi` and `editorial-english`. Reordering or hiding Home sections changes presentation, not a guarantee that associated requests stop.

[`YouTubeChartsService`](../Sources/Catalog/YouTubeChartsService.swift) selects weekly `TRACKS` entries from India and the US, with a Global fallback. These are regional chart picks, not certified language-only rankings. The displayed dates are the provider's reporting period, and selected rows retain original ranks. Velvet Thorn does not manufacture global monthly/yearly rankings.

Personal recap uses local rolling **7/30/365-day** listening windows. [`ListeningAnalytics`](../Sources/Library/ListeningAnalytics.swift) excludes paused time and seek jumps. Language shares use qualified play counts, including Unclassified in the denominator, rather than seconds or provider popularity. `RecommendationEngine` ranks candidates on device; soft language weights retain unknown/outside-language eligibility, and daily/weekly period keys keep saved mixes stable. Automatic profile-based mix seeds use recording radio; legacy explicit-language callers can use `recommendations(seed:language:)`. Candidate fetching still sends artist and recording requests. Follows and dislikes are local choices, not writes to a YouTube account.

### Release alerts

[`ReleaseWatcher`](../Sources/Recommendations/ReleaseWatcher.swift) checks at most eight due artists per run, with a six-hour catalog-check interval. A successful first read establishes the release baseline, including an empty result; a failed read does not invent a baseline. New-release state and pending notification IDs are saved together before delivery. Pending IDs are bounded by the 60 retained releases and can retry during later checks even when no catalog refresh is due.

Alerts use local iOS notifications after permission. Delivery verifies the current saved library, follow, and alert preference, checks stable identifiers against pending/delivered system notifications, and rechecks eligibility immediately before submission. Accepted notifications are durably acknowledged; failed submission or acknowledgement leaves eligible work for retry. Disabling alerts or unfollowing retires the corresponding pending records when that change saves. Already submitted system notifications are separate from that local pending state. Permission, background scheduling, and retained release bounds prevent any guarantee of eventual delivery.

## Radio and language evidence

### Live Radio (R18)

Search > Live Radio uses `LiveRadioDirectory` independently of generated music radio. Directory filters are explicit user input, never the learned listening profile. NPR discovery uses the `npr` tag and US country filter; directory tags do not certify affiliation or broadcast language. Public station metadata and the selected stream URL are separate from recording IDs and `MusicSource`.

Direct MP3/ADTS probes require consecutive-frame proof bound to the probed URL. Native validation still requires playability and video exclusion; only that proof can substitute for an empty static audio list on a direct stream. HLS needs native audio tracks and validated initial playlist references. AVFoundation owns subsequent broadcast requests, so the probe byte cap is not a broadcast-size limit. [LIVE_RADIO.md](LIVE_RADIO.md) preserves failed Live-Radio-01/02 investigations and the coordinator-reported Live-Radio-03 public KCRW success.

### Generated Music Radio

**Search > Radio** uses `SeedRadioEngine` with an explicit song or artist seed. A song starts directly; an artist resolves up to three credited recordings. Refills remain rooted in those original anchors, use existing provider `radio(seed:forceRefresh:)` APIs and apply session tuning locally. Requests are bounded and provider errors/cooldowns propagate. The device-local Listen Again store records accepted seed choices, not provider replies. [SEED_RADIO.md](SEED_RADIO.md) owns the complete current API, request budgets and filtering rules.

[`ExperienceRadioEngine`](../Sources/Recommendations/ExperienceRadioEngine.swift) first resolves station cues, gives optional hints a small budget, and expands provider radio. If those results are insufficient, it searches genre/mood songs and playlists, browses selected playlists, tries alternative anchors, and retries a bounded number of radio lanes. A starting queue needs at least four songs, an anchor, and a discovered song beyond the fixed cues. A station can start without any chosen artist; provider outages or insufficient matching songs still produce explicit retry/change-era errors. A station with no cues for the chosen languages starts from its wording alone; when no discovery can be dated, undated style songs anchor its lanes.

| Whole start / each optional artist-hint lookup | 30 seconds / 2 seconds |
| Cue searches / starting radio seeds / hint-derived seeds | Up to 6 / 4 / 2 |

YouTube Music radio responses have a five-minute in-memory lifetime; empty or unusable radio responses are not cached. Bounded final startup retries and manual continuation use `radio(seed:forceRefresh:)` to request fresh results. This bypasses cached radio data while preserving provider cooldowns and the request limits above. Automatic continuation may reuse a valid cached response. Ordinary Autoplay makes at most three radio requests per exhaustion event (ending song, one borrowed queue seed, one fresh retry after a transient failure) plus one more event when the queue actually ends; the fresh retry and the queue sheet's Autoplay retry use `radio(seed:forceRefresh: true)`. A station whose automatic continuation added nothing likewise gets one more continuation round when its queue ends. Cooldowns are never bypassed.

**Older** prefers starting releases before 2000; **Newer** prefers 2015 onward. Dated starting anchors use known recording or matching-album evidence. Year words in a style query do not verify the returned songs, although a wording-only start without dated evidence may still anchor on undated songs, and related radio/playlist results can span other years. Continuation can fall back to station-style discovery with no era restriction. Languages likewise guide discovery; unlabeled songs may appear. These preferences are not strict whole-queue filters or availability guarantees.

“This is [artist]” sorts available provider-labelled song totals descending, unknowns last. Alternate releases can carry different totals: the R10 live Radiohead check returned 2.3B for the Pablo Honey recording of Creep and 2.2B for its single. A display representative keeps its own total; counts are neither added nor used as recording identity.

`ArtistSpotlight.displaySongs` groups matching releases for display. It removes only recognized cosmetic annotations, preserving named live performances, remixes, parts, clean edits and language labels, including unsupported languages. Complete credited performer names and compatible linked IDs must agree. Every pair in a group needs valid durations within ten seconds and compatible recording-language evidence. Unknown metadata cannot bridge conflicting groups. Missing duration or ambiguous identity leaves separate rows.

Saved language corrections retain their recording ID as representative. Otherwise the ranking prefers a known album/EP, avoids known compilations and remasters, then considers explicit status, an available count, the provider listing, artwork, title length and a stable ID tie-break. Unknown release types receive no invented album classification. The winner retains its own explicit flag, artwork, duration and language metadata.

The catalog service retains source candidates across search and album updates, rather than feeding display representatives back into matching. With `N` initial recording IDs, `A` additional-song allowance and `R` configured search/album requests, retained candidates are capped at `N + (N + A) × R`; displayed additional groups remain capped at `A` (100 by default). Existing request and deadline limits still apply. The loader caches the display projection until candidates, evidence or saved corrections change. Top songs uses representatives for provider-listed groups in listing order; Featuring excludes every group with a listed member and sorts search-only collaborations by count. Role is positional: the first-named credit is primary.

Opening an artist page runs up to two songs-search pages, up to 20 exact-ID count searches, and up to three album browses when the listing is sparse. Automatic language checks wait for catalog selection to settle, then spend the existing bounded lookup budget on displayed recordings. Results remain keyed to the checked recording and its metadata. An artist's monthly audience retains the provider's unit and raw wording; monthly listeners are never relabelled as monthly plays.

The popular-song list opens with a compact, collapsed **Languages** control. At least two identified recording languages change its title to **Browse by language**; suggestions and unknowns do not count. Opening the browser shows filters, check/retry actions, and per-song evidence/corrections. Background checks do not open the browser or change its selected filter. Collapsing it retains the filter, including an empty filter; manual corrections also remain available from a song's context menu. Automatic bounded lyrics/MusicBrainz checks can run when the spotlight opens, even while the browser is collapsed.

Recording-language filters support Bengali, English, Hindi, Tamil, and Telugu. Evidence can be recording metadata, inference from matched/linked lyrics, or MusicBrainz work metadata. Artist nationality and provider region do not establish song language. Weak title labels or script hints are shown as “Likely …”; uncertain/conflicting recordings remain in All/Unclassified. Manual corrections, including “Keep unclassified,” persist per recording and can be cleared. Browser/filter state is in memory rather than saved with those corrections.

[`ArtistSpotlightLanguageClassifier`](../Sources/Catalog/ArtistSpotlightLanguageClassifier.swift) validates recording identity before unconstrained on-device recognition. An ambiguous core may receive one context retry up to 80 original words only after its own lexical/script checks pass and no confident alternative code exists. A sparse English line still needs a non-ambiguous anchor and high confidence with a clear margin. Foreign-segment vetoes run independently before positive classification. Mixed, short, or transliterated text can remain uncertain. Recognition uses no song/artist priors. [SONG_LANGUAGES.md](SONG_LANGUAGES.md) owns the thresholds and measured scope; catalog-wide accuracy is not established.

[`ArtistSpotlightMusicBrainz`](../Sources/Catalog/ArtistSpotlightMusicBrainz.swift) uses the official metadata API, not an audio service. It requires an unambiguous title/artist/duration match and a compatible exact performance link to one Song work. Missing or empty embedded language fields allow a conditional lookup of that exact work ID. An absent/ambiguous link does not trigger a work-title search, and explicit unsupported or conflicting language values are not treated as missing metadata. Results retain recording/work provenance; the correction sheet links to both entities. This is source evidence, not guaranteed ground truth.

## Song play counts

`Track.playCount` holds a provider-labelled song-play total for the selected recording. Parsing requires a complete plays label, including compact or written scales such as `1.2B plays` and `1.2 billion plays`. Linked artist/album names, upload views, audience figures and period-qualified counts cannot supply that field. Literal integer counts retain Int64 precision; malformed or overflowing values remain unknown. Displayed compact totals are rounded snapshots.

Search and album browsing can validate an audio counterpart through the existing `music/get_queue` batch. The source page's total survives that substitution only for an exact recording ID, or one explicit `MPTC` track-credits link with compatible title and artist credits. Title similarity alone is insufficient. The rescue reuses the source response and validation batch, adding no per-song request. Alternate recording counts are never summed. Weekly charts keep their separate dated `ChartEntry.views` values.

The 22 September metadata comparison found `1.2B plays` for **Tum Hi Ho** on the Aashiqui 2 song row, while its audio upload reported `200,574,245 views` and a compilation upload reported `330,833 views`. The prior album-audio rescue dropped the song total, allowing Now Playing to substitute those upload values. `PlayerController.currentPlayCount` retains the catalog scope; `resolvedViewCount` is diagnostics only, including when media comes from an older audio sidecar.

Existing cache lifetimes remain two minutes for search, ten minutes for browse and one hour for queue metadata. Saved legacy counts have no unit or fetch-time provenance and are preserved, so an old library snapshot cannot be reliably repaired without fresh matching metadata. Missing totals stay hidden. Coverage includes strict label parsing, linked-identity rejection, album/search service wiring, cache expiry and prepared-player handoff in `PlayCountTests`, `CatalogPlayCountTests`, `CatalogPlayCountServiceTests` and `PlaybackPlayCountTests`.

`YouTubeMusicService` emits `providerPlayCountUpdated` and `providerPlayCountMissing` as numeric counts in one OSLog debug record per parsed search/browse page, including zero outcomes. These records have no track IDs, titles or new dimensions, and add no remote telemetry.

## Playback and optional account

[`YouTubeStreamResolver`](../Sources/Playback/YouTubeStreamResolver.swift) chooses a compatible complete cached encoding before its expiring 24-entry in-memory URL cache or provider extraction, for normal and forced resolution. Known offline permits the local file path only; even an unexpired in-memory media URL is not an offline cache hit. The direct VISIONOS path and vendored [YouTubeKit](https://github.com/alexeichhorn/YouTubeKit) supply AAC and eligible Opus candidates. AAC can stream directly; Opus WebM is downloaded and packet-copied locally into MP4 for AVPlayer. No video player is rendered.

YouTube can require sign-in or deny a request. The optional Settings sign-in may help some account-gated playback lookups, but it is not a guarantee of availability or permission. Real-account end-to-end verification remains pending; synthetic-cookie tests do not establish that Google will accept the web sign-in flow.

- [`YouTubeAccountStore`](../Sources/Account/YouTubeAccountStore.swift) saves YouTube-domain cookie names/values, scope, expiry, and sign-in time in a separate Keychain session using `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`. The session is usable after the first unlock and does not migrate to another device. The app does not save a separate account name, email field, or password. Cookies are authentication credentials.
- The sign-in web view uses a non-persistent store. Google-domain cookies are not copied to the saved session. [`YouTubeKitAuthBridge`](../Sources/Playback/YouTubeKitAuthBridge.swift) decorates only TVHTML5 playback lookups. The opt-in import and separate account-change client use their own scoped authenticated transports. Direct source lookup, media downloads, ordinary catalog/chart/artwork/lyrics, JioSaavn, Gaana, SponsorBlock, Song details, radio and extractor feeds receive no saved session.
- Velvet Thorn does not deliberately submit YouTube watch-history or playback-tracking updates. This does not prevent Google from logging requests or associating a signed-in lookup with an account.
- Sign out removes the in-process session and legacy shared YouTube cookies, then saves a credential-free marker at `Application Support/GanaBajana/Account/pending-sign-out` before attempting Keychain deletion. A saved marker, or an unreadable sign-out status, prevents session restoration on relaunch. The marker is removed only after successful deletion.
- Settings shows **Sign-out pending** and **Retry sign-out** when marker persistence, Keychain deletion, or marker cleanup fails. If the initial marker cannot be saved, deletion is not attempted and the error explicitly requires retry before closing the app. Pending status does not claim credentials were deleted. Keychain items can survive app removal, so app deletion is not a substitute for successful sign-out.

### Account library import

**Settings > Account & connection > Import from YouTube Music** appears only while a session exists. It copies liked songs, playlists, followed artists and recent history from the signed-in account into this device's library, read-only: nothing is liked, created, subscribed or removed on the account. The page states "Google can see these requests on your account." Likes, playlists and followed artists start selected; history starts off because it creates a playlist. [`YouTubeAccountLibraryClient`](../Sources/Account/YouTubeAccountLibraryClient.swift) sends authenticated WEB_REMIX `POST /youtubei/v1/browse` requests to `music.youtube.com` for `FEmusic_liked_videos`, `FEmusic_liked_playlists` and each selected `VL…` playlist, `FEmusic_library_corpus_artists` and `FEmusic_history`, through its own ephemeral session (no cookie storage, no URL cache, two connections per host, 20 s per request, 8 MiB body cap, one retry, `Retry-After` honoured, 401/403 stop the run with **Sign in again**). `FEmusic_library_corpus_track_artists` is never requested. Bounds: 2,000 likes, 1,000 songs per playlist, 200 playlists, 500 followed artists, 500 history rows kept to 200 unique songs, 60 pages per listing. Account pages are never cached; only the WEB_REMIX version shares the catalog's 6-hour cache.

Imported content becomes ordinary library records (likes in remote order ahead of local likes, playlists named as on the account or with " (YouTube)" on a clash, follows without a release baseline, one "YouTube Music history" playlist) and syncs through iCloud like any other edit. The device-local ledger `Application Support/GanaBajana/youtube-import.json` maps remote playlist ids to local playlists and survives sign-out; it is not synced, is separate from `library.json`, and can enter normal device backups like other Application Support files. Whether Google rate-limits or flags an account that pages through 2,000 likes in one sitting is unknown; no signed-in account was available for a live check ([ACCOUNT_IMPORT.md](ACCOUNT_IMPORT.md)).

## Audio cache and quality

[`AudioCache`](../Sources/Playback/AudioCache.swift) stores immutable media encodings and sidecars under `Caches/Audio`, grouped by logical recording ID. Prepared Opus MP4 variants can coexist with an original cached encoding. Sidecars retain duration, loudness, view count, bytes, storage time, extension, optional source quality, Opus preparation version and optional validated `Track` display metadata, **not signed stream URLs**. Legacy AAC entries without quality/display metadata remain eligible. JioSaavn files and Gaana fallback files enter the same cache under `saavn~<id>` / `gaana~<id>` keys (the id's `:` becomes `~`); Gaana's own HLS streams are never stored.

[`AudioCacheLimit`](../Sources/Core/AudioCacheLimit.swift) owns the policy. Settings uses MB/GB labels with binary byte counts:

| Size choice | Actual limit | Logical-song limit |
| --- | ---: | ---: |
| 250 MB | 250 MiB | 50 |
| 500 MB | 500 MiB | 100 |
| 1 GB, default | 1 GiB (1,073,741,824 bytes) | 200 |
| 2 GB | 2 GiB | 400 |
| 5 GB | 5 GiB | 1,000 |

While not known offline, prefetch warms up to two likely songs and can fully download the first; playback also prepares upcoming/current audio. Media usage includes **all committed encodings plus active preparation files**, while song count includes distinct logical IDs. Sidecars and abandoned partial files are excluded from that media-byte total. Clearing, removal and limit changes cancel stale writers and protect all in-use variants. Artwork has its own 256 MiB disk response-cache budget and bounded image memory.

Complete audio has no TTL. [`AudioCacheRetentionPolicy`](../Sources/Playback/AudioCacheRetentionPolicy.swift) ranks unused recordings from durable listening recency and qualified-session frequency, with deterministic cache-access ties. Speculative caching cannot evict higher-scored recordings; foreground playback can admit a new choice. Both byte and logical-song limits apply, with current/upcoming/outgoing and native-reader protection allowed to leave an honest overage. The score, time windows and privacy boundary are owned by [LISTENING_DISCOVERY.md](LISTENING_DISCOVERY.md#cache-retention-from-listening).

AAC cache files preserve the downloaded bytes. Opus preparation changes the container from WebM to MP4 while copying encoded packets without re-encoding; the two container files are not byte-identical. FFmpegBridge performs local packet copy only, and AVFoundation validates native PCM output before the prepared file is committed. The original download used for preparation is temporary; existing committed fallback encodings remain protected. Runtime gates, deadlines, and variant-publication rules are in [ARCHITECTURE.md](ARCHITECTURE.md#opus-preparation-cache-variants-and-reload).

### Inventory, removal and offline continuity

**Cached songs** opens from Library (beside Downloads), from the offline bar above the tabs, or from Storage through the existing resolver's optional inventory capability; the Library card's caption reports the count and bytes from the same inventory. `AudioCache.snapshot(allowOpus:)` groups complete size-checked sidecar/media pairs across both tiers. Available-locally counts require a valid provider ID and eligible encoding; incompatible stored variants can remain visible for removal, while incomplete files are excluded. Inventory is a completeness/compatibility check, **not full native AAC decoder validation**. Playback can reject a damaged file, and missing sidecar duration uses a leased native duration read rather than a guessed catalog duration.

New sidecar metadata is preferred; older files join matching metadata already in the queue/library. A playable file without metadata has a **Cached song** fallback rather than a fabricated title. Inventory browsing performs no catalog/extraction lookup. Per-song removal drains preparation/writers, rechecks live pins and removes all variants. In-use, not-found, failed and unsupported outcomes remain distinct from successful removal or an empty inventory.

Known offline keeps Home's local routes and saved-metadata Search available while retiring automatic provider discovery. The resolver rejects misses before extraction, URL validation or download. Cached queue traversal skips missing entries within a bounded pass, preserves duplicate occurrences and respects Repeat one/all. It neither rewrites the queue nor requests Autoplay. Connectivity returning can resume interrupted preparation for existing playing intent; paused or exhausted playback does not restart by itself. Unknown network status does not prove that a provider is reachable. [Architecture](ARCHITECTURE.md#cached-inventory-and-offline-playback) records generations, inventory failures and player ownership.

### Source quality and limits

**More > Audio quality** shows "<preference title> · <source summary>", for example "Balanced · 128 kbps AAC · 44.1 kHz · Stereo", from available source encoding metadata. **Settings > Playback > Audio quality** keeps a persistent ceiling (`UserPreferences.audioQuality`): **Best available** (no ceiling), **Balanced** (160 kbps) or **Data saver** (64 kbps). Selection ranks the formats that fit the ceiling first, using the highest valid average bitrate, falling back to advertised bitrate when necessary, and preferring AAC on ties; when nothing fits, the lowest offered format plays first and the higher tiers follow in ascending order, so a broken low tier does not fail the song. A change applies to the next song; the current song and an already prepared standby item keep their stream. Complete cached and downloaded copies always play whatever their bitrate, so the ceiling never forces a network fetch or a lower copy. On iOS 26.5+, eligible Opus can be prepared for native playback; older systems use AAC. Unsupported, unavailable, or failed Opus preparation keeps the AAC fallback path. JioSaavn applies the same ceiling to its 320/160/96/48 kbps AAC tiers (320 only when the provider flags it) and Gaana to its 128/64 kbps HLS tiers. Source bitrate is not a perceptual equivalence between codecs or a measurement of speaker/headphone output.

**Reload best available audio** requests fresh selection under the active ceiling while keeping a usable cached fallback; its description names the ceiling ("Checks the source for this play, up to 160 kbps."). Unlike a normal forced retry, `refreshQuality(track:)` can bypass audio-cache selection when not known offline; offline it falls back to ordinary cached resolution and its UI control is disabled. It never replaces a saved copy with a lower bitrate: a saved 128 kbps copy under Data saver stays, a saved 48 kbps copy under Balanced is replaced by the best format under 160 kbps. A successful Opus preparation can add a higher-quality immutable variant that later cache-first plays reuse. The app does not overwrite a file AVPlayer is reading or automatically rescan the entire library. Cached media remains purgeable, downloads do not, and uncached songs need a connection.

YouTube documents Premium High quality at **up to 256 kbps** in its own [settings](https://support.google.com/youtubemusic/answer/9076559). Velvet Thorn ranks returned itag 774 Opus and itag 141 AAC tiers under the selected ceiling, but no Premium tier was observed live in these test hosts. Availability depends on the account/client. Selection guarantees neither Premium access nor bitrate, and playback is not lossless. [AUDIO_QUALITY.md](AUDIO_QUALITY.md) owns selection, metrics and coverage.

`ResolvedStream.playbackSource` records the actual byte provider. More uses it beside encoding metadata, including `via JioSaavn` or `via YouTube Music` for a Gaana fallback. Sidecars and URL-free background acquisition records preserve it through relaunch and tier changes. Unknown legacy provenance stays unknown, never inferred from a signed URL or the catalog ID. This adds no request or alternate recording identifier to the library.

Normalize Volume uses source loudness for attenuation and up to +6 dB gain-up through the shared EQ tap. The 20 ms gain ramp and channel-linked sample limiter operate per decoded item; they are not true-peak or final-crossfade protection. Missing metadata stays at unity, and HLS/live gain-up is unsupported. JioSaavn supplies no loudness; Gaana's integrated LUFS maps against the -14 LUFS reference for attenuation on its HLS path. Normalization adds no scan, provider request or fidelity improvement. [VOLUME_NORMALISATION.md](VOLUME_NORMALISATION.md) owns bounds and native coverage.

Fetched `TrackDetails` are cached on the device under `Caches/Details/*.json` (500 files, oldest removed; entries above 256 KiB or for another recording discarded on read; descriptions clipped to 16 KiB) and for 15 minutes in memory when nothing was found; offline lookups read files only. The description is provider text about a public upload, shown as received and never sent anywhere. No new identifiers, account data or listening history leave the device. [SONG_DETAILS.md](SONG_DETAILS.md) owns the screen, metrics and coverage.

## JioSaavn and Gaana catalogs

Both catalogs are unofficial and switchable for Search visibility; YouTube Music cannot be disabled. Saved `saavn:`/`gaana:` songs still route by prefix. Cross-source stream fallback and R17 JioSaavn lyric matching can send their own bounded searches independent of visibility. Both transports remain cookie-free ephemeral sessions: four connections per host, eight-second requests, streamed 4 MiB response cap, soft eight-requests-per-second limit, one transient retry and bounded memory caches. [JIOSAAVN.md](JIOSAAVN.md) and [GAANA.md](GAANA.md) own exact transport behavior.

JioSaavn (`www.jiosaavn.com/api.php`) supplies search, albums (header credits), artists (top songs, albums plus singles, latest release, similar artists), playlists (100 songs per page, at most 3 pages), radio (`reco.getreco`, Android context), plain lyrics (`lyrics.getLyrics`, attribution "JioSaavn", used as the lyrics fallback for `saavn:` ids; LRCLIB stays primary) and streams. Playback resolves at play time: a fresh `song.getDetails`, DES-ECB decryption of `encrypted_media_url` under the public 8-byte key `38346591` (`JioSaavnMediaURL`, refusing hosts outside `saavncdn.com`), tier selection under the quality ceiling (320 kbps only when the row's `320kbps` flag is true, then 160, 96, 48), then a leading `Range: bytes=0-1023` probe on `aac.saavncdn.com`. Streams report `SourceAudioQuality(codec: .aac, bitRate: 320_000 / 160_000 / 96_000 / 48_000, sampleRate: 44_100, channels: 2)`, no loudness (unity gain), `viewCount` from `play_count` and a six-hour expiry; the resolver's 24-song URL cache is memory-only and cleared when the ceiling changes, and nothing decrypted is written to disk or the library. Artwork comes from `c.saavncdn.com` at 500 px. Share links go to `https://www.jiosaavn.com/search/song/<title>`. Recording metadata, MusicBrainz work evidence, Song details' YouTube fields, Home editorial discovery and album descriptions are skipped for JioSaavn ids without error.

Gaana (`gsearch.gaana.com`, `apiv2.gaana.com`) supplies search (first page, about 50 rows per filter, artist names without ids), albums, playlists (the songs the provider lists, about 100 of a long playlist), artists (header with top songs, 20 albums, 20 similar artists: 3 requests) and radio as the seed's first credited artist's popular songs (its recommendation and lyrics endpoints need a signed-in token, so Gaana supplies no lyrics and `CompositeCatalog.lyrics` answers unavailable for `gaana:` ids). Every request carries the web player's identity headers (`deviceType: GaanaWebsiteApp`, `appVersion: V6`, `gaanaAppVersion: gaanaAndroid-8.60.2`, `deviceId: website`); details calls add `st=hls&pkc=true&request_type=web`. Playback resolves at play time: a fresh `song_detail`, AES-128-CBC decryption of the `urls.high`/`urls.medium` messages under the web bundle's 16-byte key (`GaanaMediaURL`, refusing hosts outside `akamaized.net`, `gaana.com` and `gaanacdn.com`), tier selection under the ceiling (`high` 128 kbps, `medium` 64 kbps; the adaptive `auto` ladder and the URL-less `extreme` flag are not selected), then one GET of the HLS master on `vodhlsgaana-*.akamaized.net` to prove the token opens the stream. AVPlayer fetches the master, media playlists and `segment-N.ts` files itself. Streams report `SourceAudioQuality(codec: .aac, bitRate: 128_000 / 64_000, sampleRate: 44_100, channels: 2)`, loudness from the provider's integrated LUFS against the -14 LUFS reference, `viewCount` from `popularity` and the payload's `expiryTime` (about four hours); decrypted URLs stay in the 24-song memory cache. When Gaana hands out no stream (removed song, `rest_lev` restriction, missing or expired `urls`, decryption or probe failure), the resolver asks JioSaavn and then YouTube Music for the same recording (normalised title, duration within 3 s, first artist; one songs search per fallback source) and plays and shows that source's stream. Gaana's HLS streams are never cached, downloaded or equalized; a fallback file is cached under the `gaana:` id. Artwork comes from `a10.gaanacdn.com` at 400 px. Share links go to `https://gaana.com/search/all?keyword=<title>`. 404/410 answers "This music is no longer available on Gaana." Whether Gaana blocks the identity headers for non-browser traffic over time is unknown. [JIOSAAVN.md](JIOSAAVN.md) and [GAANA.md](GAANA.md) own the endpoint tables, identity scheme, decryption notes, metrics and coverage.

## SponsorBlock

**Settings > Playback > Skip non-music sections** is off by default. While on, a YouTube recording that actually starts playing (never a paused restore, a browsed queue or known-offline playback) is looked up once on `sponsor.ajay.app` by the first four hex characters of the SHA-256 of its video id (`GET /api/skipSegments/<prefix>?categories=["music_offtopic","sponsor","selfpromo","intro","outro","interaction","preview"]&actionTypes=["skip"]`), with `Accept: application/json` and `User-Agent: Breezy/1.0 (<MusicBrainzContactURL>)` over an ephemeral cookie-free session. The service answers for every video sharing the prefix; Velvet Thorn reads only the matching entry and never the others. The service receives the prefix, the headers and the IP address, not the video id, account, cookies or library data. JioSaavn, Gaana, fixture and local ids never leave the device. Bounds: 6 s per request and 12 s per resource, 256 KiB body cap, two requests in flight, 256 submissions read per video, 24 h positive and 1 h negative memory cache of 256 video ids, `Retry-After` on 429 (60 s default), 15 s deferral after 5xx or transport failure and 60 s after other 4xx. Usable segments are `skip` actions with non-negative votes or a lock, at least 1 s long, covering at most 80 percent of the recording, merged when overlapping and capped at 32. Each segment skips once per play through the ordinary seek path on the 500 ms tick, so the jumped stretch is not credited as listening; a manual seek opens a 10 s grace; no skip during a crossfade blend or a pending offline advance. Nothing is written to disk and no SponsorBlock data enters the library, iCloud replicas, widgets or companions. No request to the live service was made during the round; the parser is fixture-tested against the public API shape. [SPONSORBLOCK.md](SPONSORBLOCK.md) owns metrics and coverage.

## Optional remote extraction

### Manual Compatibility Updates (R18)

Settings > Account & Connection > Extractor Updates imports bounded JSON packages through Files. SHA-256 checks integrity; unsigned packages require explicit source trust. Supported field aliases and exact-player-hash transforms are data, not downloaded JavaScript or generated repair code. Atomic activation, captured-generation playback confirmation and rollback preserve a durable revision floor. Complete cached files cannot confirm a new package.

No feed or publisher key is configured. `ExtractorUpdateFeed` supports a future explicit-tap HTTPS check with pinned Ed25519 keys, cookie-free transport and denied redirects, but the current app makes no update-server request. There is no launch, periodic or background polling and no promise of arbitrary upstream repair. The backup-excluded state contains packages and recovery metadata, not scripts, challenges or media URLs. [EXTRACTOR_UPDATES.md](EXTRACTOR_UPDATES.md) owns the bounded schema and trust contract.

### Remote Playback Fallback

**Remote playback fallback is off by default.** If enabled and local extraction fails, YouTubeKit connects to `remote-production.youtubekit.dev/v1` with the recording ID. `X-AppID-v1`, when available, identifies the signed app using its signing-prefix/bundle identity, not a newly generated listener ID.

[`RemoteYouTubeClient`](../Vendor/YouTubeKit/Sources/YouTubeKit/Remote/RemoteYouTubeClient.swift) can execute URLs, methods, headers, and bodies supplied by that service. It sends back response URLs, status codes, headers, bodies, and requested intermediate responses. Those additional destinations are service-directed rather than a fixed Velvet Thorn domain list. The account bridge does not add the saved YouTube session, and extraction transport disables automatic cookie/credential storage; service-directed headers and returned provider headers can nevertheless contain cookies. Responses use the receive-time limits above. Remote-service retention and use have not been verified.

## Encrypted DNS

**Encrypted DNS defaults on.** [`LyricsDNSConfiguration`](../Sources/Lyrics/LyricsDNSConfiguration.swift) sets Apple's default networking privacy context for the app, preferring system encrypted DNS or Private Relay with [Cloudflare DNS over HTTPS](https://cloudflare-dns.com/dns-query) as fallback. The Settings description states the user benefit (private hostname lookups on the current network); the mechanism stays as documented here. Despite the type name, connections beyond lyrics can use this context. The selected resolver receives hostname queries and connection metadata.

The setting affects new app connections, not device-wide DNS. It does not hide music requests from their providers. `dns.google` is an explicit live-test resolver option, not a second production fallback.

## Local data and backups

[`LibraryStore`](../Sources/Library/LibraryStore.swift) keeps the library, preferences, history/lifetime receipts and device-local playback/tips in `Application Support/GanaBajana/library.json`. Local v5 reads v1 to v4; journal/replica v4 reads v1 to v3. Legacy receipts derive from surviving events before retention without restamping event revisions. Atomic writes preserve corrupt, future and externally changed files. [ICLOUD_SYNC.md](ICLOUD_SYNC.md) owns shared/device-local fields and migration.

Listening checkpoints receive a Bool acknowledgement only after a durable save or an intentional no-op. Failed writes retain deltas for their original sessions in a memory-only buffer of up to 128 session identities. Exhausting that capacity pauses playback rather than dropping pending time; terminating the process can lose unsaved deltas. **Reload saved library** validates and rereads the saved file, reconciles preferences, and preserves a current queue/newer playback intent. An untouched failed-startup placeholder can receive a recovered queue, restored paused, without overwriting the repaired snapshot through lifecycle callbacks. A failed reload keeps the previous established document and writes blocked. [ARCHITECTURE.md](ARCHITECTURE.md#librarystore-api-and-durability) owns the recovery API.

- **Save listening history** defaults on. Turning it off stops new listening events, recent-listen entries and listening-derived language checks; existing history and resume state remain. A successful disable or clear advances the persisted privacy epoch and retires pending listening. **Clear listening history** removes events, recents and generated mixes, including retained streak records, and resets derived language/cache-retention evidence. Explicit language nudges and corrections remain. Reload also recognizes removed/reduced legacy history so pending time cannot restore erased records. Explicit library choices, search history and tip IDs are preserved.
- Detailed history and recents are retained for **400 days**. A current streak extending farther back keeps one actual session per older streak day. Retention runs when the library loads or commits.
- Lifetime time/plays survive detail pruning as exact session receipts, capped at 200,000 per generation. The shared 200,000-register journal and byte limits may bind earlier, rejecting further writes. Clear History clears receipts and rejects stale generations; History Off retains totals. Rankings still use retained detail, and earlier deleted plays cannot be recovered. [LIFETIME_STATISTICS.md](LIFETIME_STATISTICS.md) owns the contract.
- Recently opened holds at most **20** typed destinations selected from Search. Collection tracks are stripped, and legacy query text is preserved separately until removed/cleared without guessed entity migration. `clearRecentSearches()` clears both fields and advances their shared reset generation; independent compaction floors protect their ordering. Search has individual removal and Clear all. Storage shows the typed count and any legacy count, with clearing enabled for either. Listening-history settings do not gate this history. Radio setup drafts are not stored as preferences.
- Library data, its sync journal and the separate credential-free sign-out marker can enter normal device backups. iCloud sync defaults on for an absent device configuration and preserves saved opt-outs. It shares typed Search selections and per-language preferences alongside other library records, excluding playback snapshots, credentials, pending alert deliveries, StoreKit records, cached media and the derived language-cache file. Device configuration is excluded from backups. [ICLOUD_SYNC.md](ICLOUD_SYNC.md) owns the payload and retention rules. Device-only Keychain credentials do not migrate; audio/artwork and derived language caches use purgeable Caches storage.
- Device-local files remain outside library sync: Downloads, URL-free download queue/staging, import ledger, genre evidence, Song details cache, export directories and Moments. The queue, import ledger and genre file can enter normal backups; Downloads, DownloadStaging and Moments are backup-excluded. Lyric choices, TV state, SponsorBlock segments and app-resolved stream URLs stay in memory. OS background tasks separately retain request URLs.
- R18 live-radio favorites are a separate bounded file, outside library sync but eligible for backups; only public station metadata/URLs are stored, not redirect targets or song listening records. Extractor packages/state are backup-excluded and outside library sync. Account-write permission is a separate device-only Keychain record; session replacement cannot inherit it. Playback-source fields contain only the optional provider enum. Sidecars can retain display artwork URLs but never signed media URLs; background acquisition records remain URL-free, and extraction generation is memory-only.
- Moments stores at most 2,048 qualified event references within 60 days, coarse context enums, switches and bounded daily selections. Detached preparation and the library privacy epoch fence stale work. It contains no location, route names or raw motion; optional motion prompts only on explicit enable. Generation adds no provider requests. [MOMENT_MIXES.md](MOMENT_MIXES.md) owns clear/recovery and storage limits.
- StoreKit handles payment/account details. Velvet Thorn's durable purchase record is a transaction-ID-to-credit/revocation map used to avoid double-counting; it is not a purchased feature entitlement or a guaranteed cross-device purchase history.

Diagnostics use local OSLog, including outcomes, timings, and some provider identifiers/error details. Song-language diagnostics use fixed outcome counters and latency without lyric text, song titles, artist names, or entity IDs; [SONG_LANGUAGES.md](SONG_LANGUAGES.md#metrics) records the counters. [LISTENING_DISCOVERY.md#metrics](LISTENING_DISCOVERY.md#metrics) records the R6 discovery, Search, connectivity, inventory and retention counters with bounded categories/outcomes and no identity dimensions. Album-description diagnostics record local outcomes/timings without prose, album IDs, artist names, or URLs; [ALBUM_DESCRIPTIONS.md](ALBUM_DESCRIPTIONS.md#metrics) records those counters. The R12/R13 categories `Player`, `SongDetails`, `Downloads`, `AudioCache`, `Connectivity`, `StreamResolver`, `Equalizer`, `Account`, `JioSaavn`, `Gaana`, `Catalog`, `SponsorBlock`, `Playback` and `Genres` log `event=<name>` records with counts, bytes, latencies and bounded enums only: no titles, ids, queries, URLs, hash prefixes, positions, MusicBrainz tags or account data; each feature document's Metrics table lists the fields. CarPlay logs local template/navigation failures. Opus preparation records bounded failure reasons and AAC fallback; the C bridge does not log media paths, URLs, metadata, or FFmpeg message text. There is no custom remote analytics/crash endpoint. Apple/system sharing follows device settings.
